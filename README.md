# stm32-w25q32-msd

基于 STM32F103C8T6 + W25Q32 的 USB 大容量存储设备（模拟 U 盘）。

## 硬件

| 组件 | 型号 |
|---|---|
| MCU | STM32F103C8T6 |
| Flash | W25Q32 (SPI, 4MB) |
| 接口 | USB Full-Speed |

## 构建

- IDE: Keil MDK V5
- 编译器: ARMCC V5.06
- 打开 `project.uvprojx` 编译即可

## 目录结构

```
├── inc/      — 头文件
├── src/      — 源文件
├── Start/    — 启动文件 + CMSIS
├── Library/  — 标准外设库 + USB 库
│   ├── STM32F10x_StdPeriph_Driver/
│   └── STM32_USB-FS-Device_Driver/
├── docs/     — 设计文档（框架设计/需求列表/详设）
```

## 文档维护规则

本项目采用分层文档体系，各文档职责明确，**写文档前先想清楚读者是谁、要回答什么问题**：

| 文档 | 回答的问题 | 写什么 | 不写什么 |
|---|---|---|---|
| `README.md` | 这个项目是什么？怎么构建？ | 项目定位、硬件、构建方法、目录结构 | 设计细节、变更历史 |
| `CHANGELOG.md` | 这个版本**能做什么**？ | 功能层面的变化（用户/下一阶段能感知到什么）、验证结果、可观测事实 | 代码实现细节（函数名/文件路径/宏定义/寄存器值） |
| `docs/项目框架设计.md` | 系统怎么分层？组件职责？ | 架构、组件定义、依赖关系、数据流、阶段计划 | 具体代码 |
| `docs/TR1框架设计.md` | TR1 阶段怎么拆？为什么？ | 拆分原则、子阶段定义、技术决策、提交节奏、验证流程 | 具体代码 |
| `docs/详设/TR1-XX：*.md` | 这条任务**怎么实现**？ | 接口设计、代码片段、实现要点、验证步骤、排查指南 | 架构层面的讨论 |

**CHANGELOG 写作规则**：

1. **面向功能，不面向代码**：写"USB 外设硬件初始化"，不写"`src/hw_config.c` 新建 5 个函数"。读者关心的是"这个版本能做什么"，不是"改了哪些文件"。
2. **说明可感知的结果**：每条变更都要回答"用户/下一阶段能感知到什么"。例如"USB 中断通道打通，为 ISTR 事件分发（TR1-A4）提供入口"，而不是"NVIC 组 2 配置完成"。
3. **保留可观测事实**：编译验证结果、USBTreeView 实测数据、PC 设备管理器表现——这些是验收证据，不属于代码细节，应保留。
4. **代码细节去详设**：函数名、文件路径、宏定义、寄存器值、代码片段——这些是实现层面的内容，写到对应的 `docs/详设/` 文档，不进 CHANGELOG。
5. **阶段编号保留**：TR1-A1/A2/B1 等是项目内部的里程碑语言，CHANGELOG 和详设都用，保持一致。

**新增功能时**：先在 `docs/详设/` 写详细设计（实现怎么做），完成后在 `CHANGELOG.md` 记录功能变化（这个版本能做什么），两者互补不重复。
